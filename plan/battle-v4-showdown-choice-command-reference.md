# Battle V4 Showdown Choice Command Reference

## Scope

This is the Battle V4 reference table for player choices sent to the local Pokemon Showdown engine. It is based on the local Showdown client and simulator sources, not memory.

Reference sources:

- `pokemonShowdownAbout/pokemonShowdownClient/play.pokemonshowdown.com/src/battle-choices.ts`
  - `BattleChoiceBuilder.parseChoice()`
  - `BattleChoiceBuilder.stringChoice()`
  - `BattleChoiceBuilder.currentMoveList()`
- `changeBattleV2/packages/showdown-battle-core/vendor/showdown/sim/side.js`
  - `Side#choose()`
  - `Side#chooseMove()`
  - `Side#chooseSwitch()`
  - `Side#chooseTeam()`

V4 policy: generate the same canonical order as the Showdown client. Do not rely on alternate orders merely because the simulator can parse them.

## Choice List Rules

| Request state | Choice list shape | Notes |
| --- | --- | --- |
| `move` | comma-separated choices, one per commandable active Pokemon | Example: `move 1 max +1, move 2 -1`. Fainted or commanding actives are auto-filled as `pass` by client logic. |
| `switch` | comma-separated choices, one per forced switch slot | Example: `switch 3, pass`. Non-forced slots may be auto-filled as `pass`. |
| `team` / team preview | one `team ...` choice | Team preview is not comma-split like move/switch choices in sim `Side#choose()`. |
| `wait` | no choice should be sent | Showdown client throws if you try to choose during wait. |

## Canonical Commands Generated By V4

| Command | Canonical form | Examples | Source behavior |
| --- | --- | --- | --- |
| Move by index | `move <moveIndex> [special] [targetLoc]` | `move 1`, `move 1 +1`, `move 1 max +1` | Showdown client `stringChoice()` emits special suffix before target. |
| Move by id/name | Not generated by V4 | `move thunderbolt`, `move Max Lightning` | Showdown can parse IDs/names and map Z/Max names back to base move, but V4 should submit stable move indexes. |
| Switch | `switch <teamSlot>` | `switch 3` | One-based team slot. Must not switch to an already-active Pokemon. |
| Team preview | `team <slotOrder>` | `team 1234`, `team 1,2,3,4` | Showdown sim accepts compact or comma data. V4 should prefer compact slot order if it implements team preview selection. |
| Pass | `pass` | `pass` | Used for auto-filled non-commandable slots. User normally should not manually send pass. |
| Shift | `shift` | `shift` | Triples-only center shift. |
| Test fight | `testfight` or `move testfight` | `testfight` | Showdown client supports this debug/special command; V4 should not expose it in normal UI. |
| Auto/default | Not generated by V4 | `auto`, `default` | Showdown sim can auto-pick. V4 should avoid it for user-controlled battles. |

## Move Command Grammar

Canonical V4 grammar:

```text
move <moveIndex> [specialSuffix] [targetLoc]
```

Examples:

```text
move 1
move 1 +1
move 1 mega
move 1 zmove +1
move 1 max +1
move 1 terastallize +1
```

Do not generate:

```text
move 1 +1 max
move 1 +1 zmove
move 1 +1 terastallize
```

The simulator's `Side#choose()` peels target and special tokens from the end, so some alternate orders may parse. They are not the client canonical order and should not be produced by V4.

## Special Suffixes

| System | Canonical suffix | Parser aliases accepted by Showdown sim | Request fields used by UI | One-per-battle/client lock |
| --- | --- | --- | --- | --- |
| Mega Evolution | `mega` | `mega` | `canMegaEvo` | `alreadyMega`; sim choice tracks mega use. |
| Mega X | `megax` | `megax` | `canMegaEvoX` | Same Mega bucket. |
| Mega Y | `megay` | `megay` | `canMegaEvoY` | Same Mega bucket. |
| Ultra Burst | `ultra` | `ultra` | `canUltraBurst` | V4 groups this with the Mega-style transform button. |
| Z-Move | `zmove` | `zmove` | `canZMove` / `zMoves` | `alreadyZ`; sim rejects more than one Z-Move. |
| Dynamax / Max Move | `max` | `max`, `dynamax`, `gigantamax` | `canDynamax`, `maxMoves.maxMoves`, `maxMoves.gigantamax` | `alreadyMax`; sim rejects invalid / repeated Dynamax. |
| Terastallization | `terastallize` | `terastallize`, `terastal` | `canTerastallize` | `alreadyTera`; sim tracks Tera use. |

V4 canonical suffixes:

```text
mega
megax
megay
ultra
zmove
max
terastallize
```

V4 should parse only the canonical suffix position for its own draft state: token 3 after `move <index>`. The target, if any, follows the special suffix.

## Target Location

Target suffixes are signed one-based battlefield locations relative to the choosing side.

| Target suffix | Meaning in V4 usage |
| --- | --- |
| `+1` | First opposing active slot |
| `+2` | Second opposing active slot |
| `+3` | Third opposing active slot in triples |
| `-1` | First allied active slot / self-side active slot |
| `-2` | Second allied active slot |
| `-3` | Third allied active slot in triples |

Showdown client requests explicit target choice for these move targets:

```text
normal
any
adjacentAlly
adjacentAllyOrSelf
adjacentFoe
```

V4 should only append target suffixes when the request is targetable and the effective displayed move target needs an explicit target. If the move target does not allow choosing a target, the simulator rejects targetLoc.

## Z And Max Move Display

Showdown client changes the move list before submission:

- If current choice has `z`, `currentMoveList()` returns `moveRequest.zMoves`.
- If current choice has `max`, or the Pokemon is already Dynamaxed and has `maxMoves`, `currentMoveList()` returns `moveRequest.maxMoves`.
- The submitted choice still uses the base move index plus the special suffix.

V4 behavior:

| UI state | Displayed move source | Submitted choice |
| --- | --- | --- |
| Normal | `active.moves[index]` | `move <index>` |
| Z selected | `active.zMoves[index]` / normalized `move.zMove` | `move <index> zmove [target]` |
| Max selected | `active.maxMoves.maxMoves[index]` / normalized `move.maxMove` | `move <index> max [target]` |
| Already Dynamaxed | `active.maxMoves.maxMoves[index]` when Showdown request no longer has `canDynamax` but still has `maxMoves` | `move <index> [target]` unless request still requires a suffix |

## Rule Set Filtering In V4

V4 currently filters request flags and outgoing suffixes by training rule set:

| Rule set / mode | Allowed special systems |
| --- | --- |
| `gen7` | Mega / Ultra + Z |
| `gen8` | Dynamax / Max |
| `gen9` | Terastallization |
| `standard` | Terastallization |
| `coop` mode | Terastallization |

Future "multi-system chaos" modes should be explicit rule sets. Do not silently enable all systems in the standard generation modes.

## Protocol Events For Playback

These are battle protocol lines, not player choices, but they are the animation/state facts V4 should listen to after a legal choice:

| System | Protocol lines |
| --- | --- |
| Z power | `|-zpower|<pokemon>` |
| Mega Evolution | `|detailschange|...` and/or `|-mega|<pokemon>|<species>|<item>` |
| Primal Reversion | `|-primal|<pokemon>` |
| Ultra Burst | `|-burst|<pokemon>|<species>|<item>` |
| Terastallization | `|-terastallize|<pokemon>|<type>` |
| End Tera custom cleanup | `|custom|-endterastallize|<pokemon>` |
| Dynamax start | `|-start|<pokemon>|Dynamax` |
| Dynamax end | `|-end|<pokemon>|Dynamax` |

Playback state should only commit visible form / Tera / Dynamax changes at the matching animation checkpoint.

## Implementation Checklist For Command Changes

When changing Battle V4 command logic:

- [ ] Check this table first.
- [ ] Confirm local Showdown client `BattleChoiceBuilder.stringChoice()` if suffix ordering is involved.
- [ ] Confirm sim `Side#choose()` / `chooseMove()` if server validation is involved.
- [ ] Add or update identity smoke coverage for the canonical generated string.
- [ ] Keep V4 generated strings canonical even if the simulator accepts aliases or alternate order.
- [ ] Do not add compatibility for old V4 draft strings during active development unless a migration is explicitly required.
